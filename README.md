# Perspective

An opinion platform where people understand viewpoints before debating them.
Every question is split into **For / Neutral / Against**, posts explain the
reasoning behind a stance, and debate only happens inside **Challenges**.

Built as a learning project focused on system design and scalability. The full
plan, with every design decision and the reasoning behind it, is in
[docs/ROADMAP.md](docs/ROADMAP.md).

> **Status:** Phase 0 (foundation) complete. No user-facing pages yet.

## Tech stack

| Part           | Technology                                |
| -------------- | ----------------------------------------- |
| Frontend       | React, Vite, TypeScript                   |
| Backend        | Node.js, Fastify, TypeScript, Pino (logs) |
| Database       | PostgreSQL 18, Drizzle ORM                |
| Validation     | Zod                                       |
| Tooling        | pnpm workspaces, ESLint, Prettier         |
| Local services | Docker Compose                            |

## Project structure

```
apps/
  api/              Fastify server (the backend)
    src/
      config/       environment validation, logger settings
      db/           database connection and table definitions
      modules/      one folder per feature (routes + logic)
      plugins/      cross-cutting concerns, e.g. error handling
    migrations/     database history, generated by drizzle-kit
  web/              React app (the frontend)
packages/
  shared/           types and constants used by both apps
docker/             init scripts for local Postgres
docs/               roadmap and decision log
```

## Getting started

### Prerequisites

- [Node.js](https://nodejs.org/) 22 or newer
- [Docker Desktop](https://www.docker.com/products/docker-desktop/)
- pnpm, via Corepack (ships with Node):
  ```sh
  corepack enable
  ```
  The exact pnpm version is pinned in `package.json`.

### 1. Install dependencies

```sh
pnpm install
```

### 2. Create your environment file

```sh
cp .env.example .env
```

Replace every `change-me` in `.env` with a password of your own (letters and
digits only, so they work inside URLs). The passwords in `DATABASE_URL` and
`MIGRATION_DATABASE_URL` must match `APP_PASSWORD` and `MIGRATOR_PASSWORD`.

### 3. Start Postgres

```sh
docker compose up -d
docker compose ps        # wait for "(healthy)"
```

On first start, an init script creates two database roles: one that can change
the schema (used only for migrations) and one with row access only (used by
the server). See decision D19 in the roadmap.

> Passwords are applied only when the database is first created. If you change
> them in `.env` later, reset the database with `docker compose down -v`
> (**this deletes all local data**) and start it again.

### 4. Apply database migrations

```sh
pnpm db:migrate
```

### 5. Start the API

```sh
pnpm dev:api
```

Check it is running:

```sh
curl http://127.0.0.1:3000/health         # server is up
curl http://127.0.0.1:3000/health/ready   # server can reach the database
```

Both should return `{"status":"ok"}`.

## Scripts

Run from the repository root.

| Command             | What it does                                          |
| ------------------- | ----------------------------------------------------- |
| `pnpm dev:api`      | Start the API with auto-restart on file changes       |
| `pnpm db:generate`  | Create a migration from changes in `apps/api/src/db/` |
| `pnpm db:migrate`   | Apply pending migrations to the database              |
| `pnpm typecheck`    | Type-check every package                              |
| `pnpm lint`         | Lint the whole repository                             |
| `pnpm format`       | Format all files with Prettier                        |
| `pnpm format:check` | Report unformatted files without changing them        |

## Commit conventions

Commits follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<optional scope>): <short summary in the imperative>
```

| Type       | Use it for                                                |
| ---------- | --------------------------------------------------------- |
| `feat`     | A new feature or behavior                                 |
| `fix`      | A bug fix                                                 |
| `refactor` | A code change that neither adds a feature nor fixes a bug |
| `docs`     | Documentation only                                        |
| `test`     | Adding or changing tests                                  |
| `chore`    | Tooling, config, dependencies                             |

Scopes name the part of the monorepo: `api`, `web`, `shared`, `db`.

Examples:

```
feat(api): add register and login endpoints
fix(web): keep the stance column sorted after voting
chore: bump drizzle-kit
```

Rules of thumb: one logical change per commit, and the summary says _what_ the
commit does ("add", "fix", "remove"), not what you did ("added", "fixing").
