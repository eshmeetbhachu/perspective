# Perspective

An opinion platform where people understand viewpoints before debating them.
Every question is split into **For / Neutral / Against**, posts explain the
reasoning behind a stance, and debate only happens inside **Challenges**.

Built as a learning project focused on system design and scalability. The full
plan, with every design decision and the reasoning behind it, is in
[docs/ROADMAP.md](docs/ROADMAP.md).

> **Status:** Phases 0–3 complete: accounts, questions with search, and
> stances with For / Neutral / Against posts.

## Tech stack

| Part           | Technology                                |
| -------------- | ----------------------------------------- |
| Frontend       | React, Vite, TypeScript                   |
| Backend        | Node.js, Fastify, TypeScript, Pino (logs) |
| Database       | PostgreSQL 18, Drizzle ORM                |
| Validation     | Zod                                       |
| Tooling        | pnpm workspaces, ESLint, Prettier         |
| Local services | Docker Compose                            |

## Project structure

```
apps/
  api/              Fastify server (the backend)
    src/
      config/       environment validation, logger settings
      db/           database connection and table definitions
      modules/      one folder per feature (routes + logic)
      plugins/      cross-cutting concerns, e.g. error handling
    migrations/     database history, generated by drizzle-kit
  web/              React app (the frontend)
packages/
  shared/           types and constants used by both apps
docker/             init scripts for local Postgres
docs/               roadmap and decision log
```

## Getting started

### Prerequisites

- [Node.js](https://nodejs.org/) 22 or newer
- [Docker Desktop](https://www.docker.com/products/docker-desktop/)
- pnpm, via Corepack (ships with Node):
  ```sh
  corepack enable
  ```
  The exact pnpm version is pinned in `package.json`.

### 1. Install dependencies

```sh
pnpm install
```

### 2. Create your environment file

```sh
cp .env.example .env
```

Replace every `change-me` in `.env` with a password of your own (letters and
digits only, so they work inside URLs). The passwords in `DATABASE_URL` and
`MIGRATION_DATABASE_URL` must match `APP_PASSWORD` and `MIGRATOR_PASSWORD`.

### 3. Start Postgres

```sh
docker compose up -d
docker compose ps        # wait for "(healthy)"
```

On first start, an init script creates the `perspective` database plus a
separate `perspective_test` database for automated tests, and two database
roles: one that can change
the schema (used only for migrations) and one with row access only (used by
the server). See decision D19 in the roadmap.

> Passwords are applied only when the database is first created. If you change
> them in `.env` later, reset the database with `docker compose down -v`
> (**this deletes all local data**) and start it again.

### 4. Apply database migrations

```sh
pnpm db:migrate
```

### 5. Start the API

```sh
pnpm dev:api
```

Check it is running:

```sh
curl http://127.0.0.1:3000/health         # server is up
curl http://127.0.0.1:3000/health/ready   # server can reach the database
```

Both should return `{"status":"ok"}`.

### 6. Start the web app

In a second terminal:

```sh
pnpm dev:web
```

Emails (verification links, password resets) aren't sent in development: they
are printed in the API terminal, so copy the link from there.

Open <http://localhost:5173> (use `localhost`, not `127.0.0.1`: the API only
accepts changes from the exact origin in `WEB_ORIGIN`). The dev server forwards
`/api/*` to the API, so the browser only ever talks to one origin.

### Optional: Sign in with Google

Google sign-in stays hidden until the API has a Google OAuth client:

1. Open [Google Cloud Console](https://console.cloud.google.com/) and create a
   project (any name, e.g. "Perspective dev").
2. Go to **Google Auth Platform → Branding** and fill in the app name and your
   email. Under **Audience**, choose **External** and add your own Google
   account as a **test user**.
3. Go to **Clients → Create client**, pick **Web application**, and add:
   - Authorized JavaScript origin: `http://localhost:5173`
   - Authorized redirect URI: `http://localhost:5173/api/auth/google/callback`
4. Copy the client ID and secret into `.env` as `GOOGLE_CLIENT_ID` and
   `GOOGLE_CLIENT_SECRET`, then restart the API.

The client secret is a password: keep it only in `.env`.

## Scripts

Run from the repository root.

| Command                        | What it does                                                                 |
| ------------------------------ | ---------------------------------------------------------------------------- |
| `pnpm dev:web`                 | Start the web app at http://localhost:5173                                   |
| `pnpm dev:api`                 | Start the API with auto-restart on file changes                              |
| `pnpm db:generate`             | Create a migration from changes in `apps/api/src/db/`                        |
| `pnpm db:migrate`              | Apply pending migrations to the database                                     |
| `pnpm set-role <email> <role>` | Make an account `user`, `moderator`, or `admin`                              |
| `pnpm test`                    | Run the web tests, and the API tests against the `perspective_test` database |
| `pnpm build`                   | Build the web app for production into `apps/web/dist`                        |
| `pnpm typecheck`               | Type-check every package                                                     |
| `pnpm lint`                    | Lint the whole repository                                                    |
| `pnpm format`                  | Format all files with Prettier                                               |
| `pnpm format:check`            | Report unformatted files without changing them                               |

## Commit messages

Short, plain descriptions of what the commit does, in the imperative:

```
add users and sessions tables
validate signup input on the server
fix session expiry check
```

No type prefixes (`feat:`, `fix:` ...) and no emojis. One logical change per
commit. Earlier history used Conventional Commits; see D29 in the roadmap.
