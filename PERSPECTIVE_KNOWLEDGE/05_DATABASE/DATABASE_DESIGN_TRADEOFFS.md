# Database Design Trade-offs

The decisions are listed in [DATABASE_DESIGN_DECISIONS.md](../03_TECHNICAL_DECISIONS/DATABASE_DESIGN_DECISIONS.md). This page discusses the tensions between them: what was traded for what, and where the limits are.

## 1. Normalised truth vs denormalised speed

| Derived value                          | Truth lives in         | Kept in sync by                 | Rebuild tool                          |
| -------------------------------------- | ---------------------- | ------------------------------- | ------------------------------------- |
| `posts.helpful_score/count/cross_side` | `post_votes`           | same transaction as each vote   | `pnpm recompute-scores`               |
| `questions.for/neutral/against_count`  | `user_stances`         | same transaction as each stance | `recountStances()` (used by the seed) |
| `questions.search_vector`              | `title`, `description` | Postgres (generated column)     | automatic                             |

**Gain:** listings read stored numbers via indexes instead of counting millions of rows (1.1 M stances and 1.5 M votes in the lab).
**Cost:** writes do more work; logic bugs could cause drift.
**Where drift _can_ happen today:** deleting a user cascades their `post_votes` and `user_stances` rows **without** adjusting the stored counters. There is no account-deletion feature yet, so this can't happen through the app, but an admin deleting a user in SQL would leave scores and counts slightly high until the rebuild functions run. **RECOMMENDATION:** if account deletion is built, either subtract in the same transaction or run the rebuilds for affected posts and questions.

## 2. Snapshots vs live values

`posts.stance` and `post_votes.voter_stance/weight` are frozen copies. **Gain:** history keeps its meaning; unvote is exact; no recomputation on stance changes. **Cost:** a post can sit in a column whose stance its author no longer holds. That's intended (D41), but it must be explained to users.

## 3. Soft deletes vs storage and complexity

**Gain:** references never break; moderation is reversible; audits are possible. **Cost:** every query needs the `live` filter, every index must carry the same condition (D66), and deleted text stays in the database. Privacy note: "deleted" content is hidden, not erased. Real erasure (e.g. a legal request) would need a hard-delete or scrubbing tool, which doesn't exist yet.

## 4. Database-enforced rules vs flexibility

Checks, enums and unique indexes make bad data impossible, but every rule change needs a migration (changing the title length means changing both the shared Zod schema and the check constraint). The project accepts this deliberately: a rule that exists in two places agrees by review, and the database copy is the one a race condition can't bypass.

## 5. UUIDv7 vs bigint

16 vs 8 bytes per key, and per foreign key that references it. In the lab's 1.4 GB database, that overhead is a modest fraction. In exchange: no enumeration, time ordering for free, and ids generated by the database.

## 6. Polymorphic report targets vs referential integrity

One queue for four content types, at the cost of no FK on `target_id`. The code tolerates missing targets.

## 7. Postgres for everything vs specialised stores

Postgres serves as the relational store, the search engine (tsvector), the fuzzy matcher (trigrams), the rate-limit counter for daily limits, and the source of session state. **Gain:** one system to run, back up and reason about; transactions span all of it. **Limit measured:** search is the most expensive query; the threshold for adding a search engine is written down (≈40% of DB time, D72). Redis was added only in the lab, for things Postgres is worse at: shared, short-lived, very hot data (cache, request-rate limits, queue).

## 8. One primary vs replicas

Writes always go to one primary. The lab replica doubled successful throughput for reads, at the cost of **replication lag**, which needs the LSN check (and therefore Redis) to give read-your-writes. Production has no replica. See [SCALING_AND_INFRASTRUCTURE_EXPERIMENTS.md](../09_TESTING_AND_DEPLOYMENT/SCALING_AND_INFRASTRUCTURE_EXPERIMENTS.md).

## 9. Free-tier database vs durability

Neon free keeps a 6-hour restore window, one manual snapshot, and no scheduled backups. A bad migration or an accidental `DELETE` discovered after 6 hours couldn't be undone. This is the biggest operational risk in the current deployment and the main open Phase 8 item. **RECOMMENDATION:** a scheduled `pg_dump` to private storage, plus a _tested_ restore.

## 10. Things that would need to change at much larger scale

| Pressure                                      | Likely change                                                                                         |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Hot questions with huge columns               | Store a periodically refreshed hot score with an index                                                |
| Very large `sessions` table                   | Periodic cleanup of expired rows (today they're deleted only when presented); or partitioning by time |
| Notifications growing forever                 | Archive or delete old read notifications                                                              |
| Expired `oauth_pending` / `email_tokens` rows | A cleanup job                                                                                         |
| Search beyond ~40% of DB time                 | A search engine fed by a job queue (D72)                                                              |
| Write volume beyond one primary               | Partitioning or sharding by question; far beyond current needs                                        |
