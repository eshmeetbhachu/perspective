# Backend Architecture

The API (`apps/api`) is a Fastify 5 server written in TypeScript. In development it runs straight from source with `tsx`. In production it runs as a bundled JavaScript file inside a Docker container.

## Folder layout

```
apps/api/
  src/
    server.ts          starts the app: listen, error listeners, graceful shutdown
    app.ts             buildApp(): plugins, hooks, routes (no listening, so tests can use it)
    config/
      env.ts           every environment variable, validated with Zod at startup
      logger.ts        Pino options: redaction of secrets, URL redaction, pretty logs in dev
    db/
      client.ts        pg Pool + Drizzle instance (+ optional replica), Executor type
      schema.ts        every table, index and constraint, in TypeScript
      errors.ts        uniqueViolation(): read a Postgres unique-index error
    errors.ts          AppError: an expected error that is safe to show the client
    plugins/           cross-cutting request hooks
      auth.ts          loadSession, requireUser, requireVerifiedEmail, requireRole
      csrf.ts          checkOrigin: non-GET requests must come from WEB_ORIGIN
      proxy-secret.ts  requireProxySecret: requests must come through Vercel (prod)
      error-handler.ts errorHandler, notFoundHandler: the error contract (D22)
    modules/           one folder per feature (routes + logic + queries)
      auth/ questions/ stances/ posts/ votes/ challenges/ notifications/ moderation/ health/
    cache.ts           Redis client, response cache, replica routing (Phase 9)
    mailer.ts          sendEmail / deliverEmail, optional BullMQ queue
    worker.ts          separate process that sends queued emails
    telemetry.ts       Prometheus metrics (private port)
    instrumentation.ts OpenTelemetry tracing, preloaded with --import
    migrate.ts         deploy-time migrations under an advisory lock
  migrations/          SQL generated by drizzle-kit (+ meta snapshots)
  scripts/             build, seed, roles, set-role, recompute-scores, load helpers
  test/                Vitest integration tests against perspective_test
```

## Startup: `server.ts` and `app.ts`

```mermaid
sequenceDiagram
  participant N as node dist/server.js
  participant E as config/env.ts
  participant A as buildApp()
  participant L as app.listen
  N->>E: import → parse process.env with Zod
  alt invalid
    E-->>N: print which variables are wrong, exit(1)
  end
  N->>A: register error handler, Zod compilers,<br/>helmet, cors, cookie, rate-limit,<br/>hooks, all route modules
  N->>N: attach 'error' listeners to pg pools and Redis
  N->>N: startMetricsServer() (only if METRICS_PORT)
  N->>L: listen on HOST:PORT
  Note over N: on SIGINT/SIGTERM: app.close(), pool.end(),<br/>exit 0; force exit after 10 s
```

Three design points:

1. **`buildApp()` doesn't listen** (`app.ts:32`). Tests call `buildApp()` and send fake requests with `app.inject()`: no ports, no network, and everything else (hooks, validation, database) behaves exactly as in production.
2. **Configuration is validated before anything else runs.** `env.ts` is imported first (indirectly, by every module). If `DATABASE_URL` is missing or `PORT` is not a number, the process prints which variable is wrong (never its value, which could be a secret) and exits. A misconfigured server that half-works is worse than one that refuses to start.
3. **Graceful shutdown** (`server.ts:41`). Hosting platforms stop containers with `SIGTERM`. `app.close()` stops accepting connections and lets in-flight requests finish; then the database pool is closed. A 10-second timer (`unref()`'d so the timer itself doesn't keep Node alive) forces an exit if something hangs.

**Why listen for `pool.on("error")`** (`server.ts:16`)? When Postgres drops an _idle_ connection (restart, network blip, Neon scaling to zero), `pg` emits an `error` event on the pool. In Node, an `error` event with no listener crashes the whole process. This was a real bug found during development (see [BUGS_AND_FIXES.md](../08_BUGS_AND_DEBUGGING/BUGS_AND_FIXES.md)). With the listener the error is logged, and the pool opens a fresh connection for the next query.

## Plugins and hooks registered in `buildApp()`

| Order | What                                                            | Why                                                                                                                   |
| ----- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 1     | `Fastify({ logger, trustProxy })`                               | `trustProxy` is `true` with `ORIGIN_SECRET`, else the `TRUST_PROXY` list, else `false` (D58, D61)                     |
| 2     | `recordRequests(app)`                                           | `onResponse` hook timing every request for Prometheus (cheap; the metrics are only _served_ if `METRICS_PORT` is set) |
| 3     | `setErrorHandler`, `setNotFoundHandler`                         | One error shape for everything (D22)                                                                                  |
| 4     | `setValidatorCompiler`, `setSerializerCompiler`                 | Zod validates requests **and** shapes responses                                                                       |
| 5     | `removeContentTypeParser("text/plain")`                         | Only JSON bodies are accepted (CSRF defence, D30)                                                                     |
| 6     | `helmet`                                                        | Security headers                                                                                                      |
| 7     | `cors({ origin: WEB_ORIGIN, credentials: true })`               | Only our website may read responses cross-origin                                                                      |
| 8     | `cookie`                                                        | Parse and set cookies                                                                                                 |
| 9     | `rateLimit({ global: false, redis, skipOnError })`              | Limits are opt-in per route; shared via Redis when present (D68)                                                      |
| 10    | `decorateRequest(...)`                                          | Declares `request.user`, `sessionId`, `cacheKey`, `readFromReplica` up front (fast object shapes)                     |
| 11    | `onRequest`: `requireProxySecret`, `checkOrigin`, `loadSession` | In this order: reject proxy-skippers, then cross-site writes, then identify the user                                  |
| 12    | `preHandler`: `serveFromCache`                                  | Must run after `loadSession`, because only logged-out visitors are served from the cache                              |
| 13    | `onSend`: `storeInCache`, default `cache-control: no-store`     | Store successful misses; stop shared caches (CDNs) keeping per-user responses (D61)                                   |
| 14    | `register(...Routes)` × 12                                      | Every module's routes                                                                                                 |

**Why `decorateRequest` with defaults?** Fastify (and V8, the JavaScript engine) work fastest when every request object has the same set of properties from the start. Adding properties later changes the object's internal "shape" and slows property access. Declaring them up front also documents what exists.

## Anatomy of a route

Every route follows the same pattern. The example is `POST /questions/:slug/posts` from `modules/posts/routes.ts:86`:

```ts
app.post(
  "/questions/:slug/posts",
  {
    preHandler: requireVerifiedEmail,          // 1. guard: logged in + verified
    schema: {
      params: slugParams,                      // 2. Zod: validates and types the input
      body: createPostSchema,
      response: { 201: postResponseSchema },   // 3. Zod: shapes the output
    },
  },
  async (request, reply) => {                  // 4. handler: only runs if 1-2 passed
    const user = requireUser(request);         //    narrows `user` to non-null for TypeScript
    ...business rules, transaction...
    await bumpCache(request.log, `question:${request.params.slug}`);  // 5. after commit
    return reply.status(201).send({ post: ... });
  },
);
```

1. **Guards** run as `preHandler` hooks. If they throw an `AppError`, the handler never runs.
2. **Input schemas** reject bad input with a 400 `VALIDATION_FAILED` and per-field `details`. Inside the handler, `request.body` is already typed as the schema's output type (thanks to `FastifyPluginAsyncZod`).
3. **Response schemas** strip any property that isn't in the schema before sending. That protects against accidentally leaking a column (for example `password_hash`) if a query ever selects too much.
4. **Business rules** that need the database (daily limits, "is this your post?") are checked in the handler and throw `AppError` with a specific code.
5. **Cache invalidation and other after-effects** happen after the transaction commits.

## Errors: one contract

`AppError(statusCode, code, message, details?)` (`src/errors.ts`) represents an _expected_ failure. The handler in `plugins/error-handler.ts` decides what the client sees:

| Thrown                                                                       | Response                                                                 |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `AppError`                                                                   | its status, code and message                                             |
| Zod validation failure (`error.validation`)                                  | 400 `VALIDATION_FAILED`, one `{ path, message }` per invalid field       |
| Other 4xx detected by Fastify (bad JSON, body too large, wrong content type) | that status, `BAD_REQUEST`, Fastify's message                            |
| Anything else                                                                | logged in full; client gets 500 `INTERNAL_ERROR`, "Something went wrong" |

Why hide details of unexpected errors? Stack traces and SQL error messages reveal table names, library versions and code paths, which helps an attacker. They go to the server log instead. The full rationale is in [VALIDATION_AND_ERROR_HANDLING.md](../06_TYPESCRIPT_AND_BACKEND/VALIDATION_AND_ERROR_HANDLING.md).

## Database access

- `db/client.ts` creates one `pg.Pool` (a set of open connections that queries borrow and return) and one Drizzle instance with `casing: "snake_case"`, so `createdAt` in TypeScript is `created_at` in SQL.
- The `Executor` type (`client.ts:26`) is "either `db` or an open transaction". Helpers such as `moveStanceCount(tx, ...)`, `notify(tx, ...)` and `insertUser(values, executor)` accept it, so they can run inside the caller's transaction.
- **Every query is parameterized.** Drizzle sends values separately from the SQL text, so input can never change the query's structure (no SQL injection). Even raw `sql\`...\`` templates in the code interpolate values as parameters, not text.
- **Unique-index errors become friendly errors** through `uniqueViolation(err)` (`db/errors.ts`), which reads Postgres error code `23505` and the constraint name from `err.cause` (Drizzle wraps the driver error). For example `posts_author_question_stance_unique` becomes 409 `ALREADY_POSTED`.

## Production build

`scripts/build.ts` runs esbuild over four entry points (`server`, `migrate`, `worker`, `instrumentation`). It bundles our code **and** `@perspective/shared` (TypeScript source, D17) into `dist/*.js`, while npm packages stay as normal `import`s from `node_modules` (`external`). Why keep packages external? Some contain native code (argon2) that can't be bundled, and bundling them gains nothing. The Docker image then installs only production dependencies (`pnpm deploy --prod`). See [INFRASTRUCTURE_AND_DEPLOYMENT.md](INFRASTRUCTURE_AND_DEPLOYMENT.md).

File-by-file guide: [BACKEND_FILE_GUIDE.md](../02_CODEBASE/BACKEND_FILE_GUIDE.md).
